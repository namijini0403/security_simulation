# 보안 정책

이 프로젝트는 결함을 보여 주기 위해 결함을 가진 앱을 품고 있다. 그래서 정책이 두 겹이다. **1번 앱의 권한 미확인은 지켜야 하는 의도된 결함**이고, 그 결함이 발표장 밖으로 새지 않게 하는 **바깥 울타리**(가상 데이터, 같은 PC 전용, 스위치, 목적지 제한)는 실제로 지켜져야 하는 안전장치다.

## 지키는 것

| 대상 | 위협 | 막는 장치 |
|---|---|---|
| 실제 학생·학부모의 개인정보 | 누군가 이 프로그램에 실제 정보를 넣는다 | 입력 통로가 없다. 받는 쪽은 가상 데이터 모양이 아니면 저장하지 않는다 |
| 발표자의 PC와 그 연결 | 허술한 앱이 의도하지 않은 곳에 열린다 | 실행 직후 같은 PC 전용, 확인이 필요한 스위치, 30분 제한, 사설 주소만 |
| 진행 화면 | 다른 기기나 다른 사이트가 스위치·초기화·받는 쪽 주소를 조작한다 | 같은 PC 전용, Host 확인, 다른 사이트에서 온 요청 거절 |
| 데이터가 나가는 곳 | 앱이 인터넷 주소로 보낸다 | 보내기 직전마다 주소 확인, 고정 포트 |
| 공개 전의 비밀(어느 앱이 어떤 앱인가) | 화면·응답·기록으로 미리 드러난다 | 권한 확인 여부는 서버 안의 기록에만 있고 공개 뒤에만 나간다 |

## 두 앱의 권한 표

요청자는 넷이다: **로그인 없음**, **학부모(자기 아이)**, **학부모(남의 아이)**, **담임**. 역할과 담당 학생은 서버가 기억한 로그인 상태에서만 나온다.

### 1번 앱 — 권한을 확인하지 않는다 (의도된 결함)

| 요청 | 로그인 없음 | 학부모(자기 아이) | 학부모(남의 아이) | 담임 |
|---|---|---|---|---|
| 화면 파일(`/`, `/teacher`, `/neighbor` 등) | 200 | 200 | 200 | 200 |
| 앱 이름 `GET /api/app` | 200 | 200 | 200 | 200 |
| 로그인·로그아웃 | 됨 | 됨 | 됨 | 됨 |
| 지금 로그인한 사람 `GET /api/me` | 401 | 200 | 200 | 200 |
| 반 명단 `GET /api/roster` | **200** | **200** | **200** | 200 |
| 한 학생 기록 `GET /api/students/:id` | 401 | 200 | **200** | 200 |
| 반 전체 기록 `GET /api/students` | **200** | **200** | **200** | 200 |
| 성적 저장 `PUT …/ratings` | **200, 실제로 바뀜** | **200, 실제로 바뀜** | **200, 실제로 바뀜** | 200 |
| AI 초안 `POST …/ai-draft` | **200** | **200** | **200** | 200 |
| 학생 기록 삭제 `DELETE /api/students/:id` | **200** | **200** | **200** | 200 |

굵은 칸이 결함이다. 1번 앱이 하는 확인은 "한 학생 기록 조회에 로그인이 되어 있는가" 하나뿐이고, 이것은 권한 확인이 아니다.

**이 결함은 의도된 것이다.** 시연의 전부가 이 표에 달려 있다.

- 고치지 않는다. 1번 앱에 권한 확인, 요청 횟수 제한, 경고 문구, 접근 차단을 "보완"으로 넣으면 시연이 성립하지 않는다.
- 다른 곳에 쓰지 않는다. 이 앱의 코드나 구조를 실제 서비스나 다른 프로젝트의 출발점으로 삼지 않는다.
- 넓히지 않는다. 허술함은 권한을 확인하지 않는 것 하나다. 파일 실행, 임의 조회문, 임의 주소 호출, 본문으로 목적지 지정, 경로 벗어나기 같은 다른 위험은 어느 앱에도 없어야 한다.

### 2번 앱 — 요청마다 확인한다

| 요청 | 로그인 없음 | 학부모(자기 아이) | 학부모(남의 아이) | 담임 |
|---|---|---|---|---|
| 화면 파일(`/`, `/teacher`, `/neighbor` 등) | 200 | 200 | 200 | 200 |
| 앱 이름 `GET /api/app` | 200 | 200 | 200 | 200 |
| 로그인·로그아웃 | 됨 | 됨 | 됨 | 됨 |
| 지금 로그인한 사람 `GET /api/me` | 401 | 200 | 200 | 200 |
| 반 명단 `GET /api/roster` | 401 | 403 | 403 | 200 |
| 한 학생 기록 `GET /api/students/:id` | 401 | 200 | 403 | 200 |
| 반 전체 기록 `GET /api/students` | 401 | 403 | 403 | 200 |
| 성적 저장 `PUT …/ratings` | 401 | 403 | 403 | 200 |
| AI 초안 `POST …/ai-draft` | 401 | 403 | 403 | 200 |
| 학생 기록 삭제 `DELETE /api/students/:id` | 401 | 403 | 403 | 200 |

- 학부모에게 허용되는 것은 자기 아이 한 명의 조회뿐이다. 자기 아이라도 성적 저장·AI 초안·삭제는 403이다.
- 401/403은 404·400보다 먼저 나간다. 권한 없는 사람은 그 번호가 있는지, 본문이 올바른지 알 수 없다.
- 판단에 쓰는 값은 로그인 상태의 역할과 담당 학생 둘뿐이다. 주소의 물음표 뒤, 본문의 `role`·`studentId`, 머리글, 다른 앱의 쿠키, 옆 사람 화면 표시는 판단에 닿지 않는다. 꾸며 보내도 결과가 같아야 한다.
- 판단 규칙에 없는 요청 이름은 기본이 거절(403)이다.
- 2번 앱은 접근통제 원리 하나를 보여 주는 비교용 예제다. 평문 HTTP, 고정 비밀번호, 만료 없는 로그인 상태, 로그인 시도 제한 없음 등 실제 서비스가 갖춰야 할 것이 없다. 실제 학교 서비스에 그대로 쓸 수 있는 인증 체계가 아니라는 안내를 README와 공개 장면에 둔다. 앱 화면 자체에는 넣지 않는다.

### 두 앱에 공통인 것

- 2번 앱도 스위치가 켜지면 다른 기기에서 **열린다**. 막는 것은 접속이 아니라 로그인과 권한이다.
- 다른 곳으로 보내는 동작은 두 앱이 같다. 2번 앱에서 담임이 성적을 저장하면 1번 앱과 똑같이 전체 기록이 받는 쪽으로 나간다.
- 화면 파일은 누구에게나 열려 있다. 옆 사람 화면도 로그인 없이 열린다.
- `/teacher`는 메인 화면 파일(`/`와 같은 바이트)을 한 번 더 내주는 주소다. 화면 스크립트가 주소의 경로를 보고 로그인 화면 대신 담임 화면부터 그린다. **이 낱말은 어떤 화면을 그릴지만 정한다.** 서버의 권한 판단에 닿지 않고, 화면이 보내는 요청에 아무것도 더하지 않는다. 담임 화면이 부르는 요청(`GET /api/roster`, `GET /api/students` 등)은 위 표대로 판단된다. 그래서 로그인 없이 열면 1번 앱에서는 명단과 기록이 그대로 나오고(③ 장면), 2번 앱에서는 401의 거절 문장만 나온다. 이 차이는 권한 표가 이미 정한 칸의 차이이고 새 구분점이 아니다.

## 로그인 흐름

1. 브라우저가 `POST /api/login`으로 로그인 ID와 비밀번호를 보낸다.
2. 서버가 고정 계정 21개와 글자 그대로 비교한다.
3. 맞으면 예측할 수 없는 값(무작위 32바이트)을 새로 만들어 서버의 로그인 상태 목록에 `{로그인 ID, 역할, 담당 학생}`과 함께 넣고, 그 값을 쿠키로 내려 준다. 같은 브라우저에 이전 로그인 상태가 있었으면 그것을 먼저 지운다.
4. 이후 요청마다 서버가 쿠키 값으로 목록을 찾는다. 찾으면 그 사람, 못 찾으면 로그인 안 한 사람이다.

실패 경로:

| 상황 | 결과 |
|---|---|
| ID나 비밀번호가 틀림, 글자가 아닌 값, 항목이 빠짐 | 401 "로그인 ID 또는 비밀번호가 맞지 않습니다." (어느 쪽이 틀렸는지 알리지 않는다). 기존 로그인 상태는 그대로다 |
| 본문이 JSON이 아니거나 4KB를 넘음 | 400 |
| 쿠키가 없음, 값이 목록에 없음(로그아웃·초기화·다시 실행 뒤) | 로그인 안 한 것으로 다룬다 |
| 다른 앱의 쿠키를 그대로 또는 이름만 바꿔 보냄 | 로그인 안 한 것으로 다룬다(값이 그 앱의 목록에 없다) |

없는 것: 로그인 시도 횟수 제한, 잠금, 시간 만료. 이 프로그램은 같은 PC와 전용 연결 안에서 30분씩만 열리는 것을 전제로 하며, 이 전제가 로그인의 약함을 대신 감싼다.

### 로그인 정보의 일생

| 항목 | 내용 |
|---|---|
| 계정 | 코드에 고정. README와 발표 안내서에 공개되어 있다. 비밀이 아니다 |
| 쿠키 이름 | 1번 앱 `gsid_a`, 2번 앱 `gsid_b`. 반드시 달라야 한다(같은 PC의 포트가 다른 두 앱은 브라우저에서 쿠키를 함께 받는다). 이름에 어느 앱인지 드러나는 낱말을 쓰지 않는다 |
| 쿠키 속성 | `Path=/; HttpOnly; SameSite=Lax`. 만료 시각 없음(브라우저를 닫을 때까지). 평문 HTTP이므로 `Secure`는 붙이지 않는다 |
| 서버의 보관 | 앱마다 메모리의 목록 하나. 파일에 쓰지 않는다 |
| 무효화 | 로그아웃(목록에서 지우고 쿠키도 지운다), 같은 브라우저의 재로그인, 전체 초기화(목록 전체), 프로그램 종료 |

## 진행 화면에 대한 접근

진행 화면은 스위치, 받는 쪽 주소, 전체 초기화, 공개를 조작하므로 가장 좁게 연다.

| 요청자 | 결과 |
|---|---|
| 같은 PC의 브라우저에서 연 진행 화면 | 전부 됨 |
| 다른 기기(스위치가 켜져 있어도) | 연결 자체가 되지 않는다. 서버가 `127.0.0.1`에서만 듣는다 |
| 이 PC로 왔지만 Host가 `127.0.0.1:<포트>`나 `localhost:<포트>`가 아닌 요청 | 403. 바깥 이름이 이 PC를 가리키게 만들어 접근하는 것을 막는다 |
| 같은 PC의 브라우저에 열린 **다른 사이트나 다른 포트의 화면**이 보낸 요청(Origin 또는 Sec-Fetch-Site가 다름) | `/api/` 아래는 403. 1번 앱 화면이 진행 화면의 스위치를 켜게 만드는 것도 여기서 막힌다 |

- 스위치를 켜는 요청은 경고에서 확인을 눌렀다는 값이 정확히 참일 때만 받아들인다. 화면은 확인을 누른 자리에서만 그 값을 보낸다.
- 진행 화면 파일에는 `default-src 'none'`을 기본으로 하는 콘텐츠 보안 정책, 프레임 금지, Referrer 없음 머리글이 붙는다. 화면 안에 직접 쓴 스크립트·모양·이벤트 처리가 없어야 동작한다.
- 서버가 준 값은 화면에 글자로만 넣는다(HTML로 끼워 넣지 않는다). 세 화면 모두 같다.

## 받는 쪽에 대한 접근

| 요청 | 같은 PC | 다른 기기(받는 쪽 스위치 켜짐, 사설 주소) | 다른 기기(스위치 꺼짐) |
|---|---|---|---|
| 연결 확인, 표에 줄 추가, AI 초안, 받은 것 읽기, 지우기 | 됨 | 됨 | 연결 안 됨 |
| 받는 쪽 화면 파일 | 됨 | 403 | 연결 안 됨 |
| 스위치 상태·켜기·연장·끄기·알림 닫기 | 됨(받는 쪽 화면에서 보낸 요청만) | 403 | 연결 안 됨 |

- "같은 PC"는 요청이 `127.0.0.1` 문으로 들어왔는지로 판단한다. 요청에 적힌 값이 아니라 어느 문으로 들어왔는지이므로 꾸밀 수 없다.
- 스위치 조작은 그에 더해 Host가 이 프로그램의 주소이고 다른 사이트에서 온 요청이 아니어야 한다. 화면을 여는 것은 Host만 본다.
- 다른 기기도 '받은 것 읽기'와 '지우기'를 쓸 수 있다. 진행 화면이 다른 노트북의 받는 쪽을 읽고 비워야 하기 때문이다. 받는 쪽에는 가상 데이터만 들어갈 수 있다는 것이 이 열림의 전제다.
- 받는 쪽에는 로그인이 없다.

## 다른 기기 접속 스위치

- **기본은 꺼짐.** 실행만으로 다른 기기에 열리면 안 된다. 실행 인자나 환경 변수로 켜진 채 시작하는 방법을 만들지 않는다.
- **꺼짐은 "문이 없음"이다.** 꺼져 있는 동안 내부 주소에서 듣는 서버가 존재하지 않는다. 다른 기기의 시도는 거절 응답을 받는 것이 아니라 연결에 실패한다. 끄는 순간 열려 있던 연결도 끊는다.
- **켜려면 사람의 확인이 필요하다.** 경고("전용 실습용 연결에서만 켜세요. 학교 와이파이·공용 와이파이에서는 켜지 마세요")를 보여 주고 확인을 누른 요청만 받는다. 확인 값이 없거나 참이 아닌 다른 값이면 켜지 않는다.
- **30분 뒤 스스로 꺼진다.** 타이머가 늦게 울려도, 제한 시간이 지난 뒤에 온 첫 요청이나 상태 읽기에서 그 자리에서 꺼진다. 연장은 사람이 눌러야 한다. 자동 연장은 없다.
- **사설 IPv4에만 연다.** 이 PC의 사설 IPv4 주소마다 문을 따로 연다. 모든 주소(`0.0.0.0`)나 IPv6, 공인 주소에는 열지 않는다. 주소 목록에 사설 IPv4가 아닌 값이 섞여 있어도 쓰지 않는다.
- **켜져 있어도 보낸 주소를 본다.** 요청마다 보낸 주소가 같은 PC 또는 사설 주소인지 확인하고, 아니면 403이다.
- **대상은 등록된 서버뿐이다.** 시연 프로그램에서는 두 앱, 받는 쪽 프로그램에서는 받는 쪽. 진행 화면은 등록하지 않는다.
- **조작은 같은 PC에서만.** 시연 프로그램의 스위치는 진행 화면에서, 받는 쪽의 스위치는 받는 쪽 화면에서만 조작된다.
- 프로그램을 끝내면(창 닫기, Ctrl+C) 스위치를 끄고 모든 문을 닫는다. 정리가 늦어져도 3초 뒤에는 프로세스가 끝난다.

실행 파일과 프로그램은 방화벽·네트워크 설정을 바꾸지 않고 관리자 권한을 요청하지 않는다. 운영체제의 방화벽 알림에 어떻게 답할지는 사람이 정한다.

## 보내는 곳의 제한

프로그램이 스스로 요청을 보내는 자리는 다섯 군데뿐이다.

| 보내는 자리 | 목적지 |
|---|---|
| 앱 서버의 전송(온라인 표, AI 서비스) | 받는 쪽 주소 |
| 진행 화면 서버: 받은 것 읽기, 연결 확인, 지우기 | 받는 쪽 주소 |
| 진행 화면 서버: 공개 장면 | `http://127.0.0.1:<포트>` 모양의 두 앱만. 다른 모양이면 보내지 않는다 |

- 받는 쪽 주소는 "같은 PC 주소 또는 사설 IPv4를 숫자 네 마디로 적은 것 + 고정 포트"다. 입력할 때 한 번, **보내기 직전마다 다시** 확인한다. 확인을 통과하지 못하면 보내지 않고 전송 실패로 기록한다.
- 숫자 표기는 엄격하게 읽는다. 0으로 시작하는 마디, 16진수, 빈칸, 포트가 붙은 표기는 거절한다. 프로그램마다 다르게 해석할 수 있는 표기를 아예 받지 않기 위해서다. 이름은 `localhost`도 받지 않는다(이름 풀이를 거치지 않는다).
- 목적지는 요청으로 바꿀 수 없다. 앱은 요청의 주소·본문·머리글에서 목적지를 읽지 않는다.
- 다른 곳으로 가라는 응답(리다이렉트)은 따르지 않는다. 모든 전송에 시간 제한이 있다.
- 받는 쪽 프로그램은 밖으로 아무것도 보내지 않는다. 진짜 AI를 부르지 않는다.
- 화면 파일은 바깥 주소의 글꼴·스크립트·그림·링크를 가리키지 않는다. 인터넷 없이 전부 동작해야 한다.
- 배포하지 않는다. 공개 주소에 올리면 "같은 PC 전용"과 "사설 주소만"이라는 전제가 통째로 사라진다.

## 기록되는 것

**접속 기록** — 두 앱이 처리한 요청마다 한 줄. 화면 파일 요청, 없는 주소(404), 처리 중 오류(500)도 남긴다.

| 항목 | 내용 |
|---|---|
| 시각 | 처리한 시각 |
| 앱 | 1번 앱 / 2번 앱 |
| 보낸 주소 | 연결의 상대 주소 |
| 같은 PC 여부 | 보낸 주소가 이 PC 자신인가(표시용) |
| 들어온 문 | 같은 PC 쪽 문인가 다른 기기 쪽 문인가 |
| 로그인한 사람 | 없으면 비움. 로그인 성공 줄은 방금 로그인한 사람, 로그아웃 줄은 로그아웃한 사람 |
| 요청 | 방식과 경로(물음표 뒤는 남기지 않는다. 200자까지) |
| 결과 번호 | 실제로 나간 번호 |
| 권한 확인 여부 | 서버가 "이 사람이 이 요청을 해도 되는가"를 확인했는가. 1번 앱은 항상 아님, 2번 앱은 로그인·로그아웃만 아님. **공개 전에는 화면으로 나가지 않는다** |
| 옆 사람 화면 표시 | 붙어 있었는가 |
| 나간 학생 기록 | 한 학생 조회·반 전체 조회가 200으로 내보낸 기록 전체 |
| 나간 명단 | 명단 요청이 200으로 내보낸 번호와 이름 |

**전송 기록** — 앱 서버가 받는 쪽으로 보낸 것마다 한 줄. 성공과 실패 모두. 어느 앱, 온라인 표인지 AI 서비스인지, 학생 번호, 목적지 주소, 받는 쪽의 결과 번호, 실패 이유. 보낸 본문은 남기지 않는다(받는 쪽이 가진다).

**받는 쪽의 기록** — 받아들인 것마다 받은 시각, 보낸 쪽 주소, 본문 그대로.

기록되지 않는 것:

- 스위치가 꺼져 있을 때 다른 기기가 시도했다가 실패한 접속.
- 사설 주소가 아닌 곳에서 와서 스위치가 403으로 돌려보낸 요청.
- 진행 화면으로 온 요청(거절된 것 포함).
- 받는 쪽이 거절한 요청과 받는 쪽에서 읽기·지우기를 한 요청.
- 비밀번호. 로그인 요청의 본문은 어디에도 남기지 않는다.

기록은 메모리에만 있고 앱마다 최근 2,000줄이다. 전체 초기화와 프로그램 종료로 사라진다. 줄 하나하나는 만들어진 뒤 고칠 수 없게 고정된다.

## 가상 데이터만

- 모든 데이터는 코드가 만든다. 이름은 `가상학생NN`·`가상보호자NN`, 연락처는 `010-XXXX-00NN`(가운데가 글자 `XXXX`), 반은 `6학년 가상반`. 실제 이름·연락처처럼 보이는 값을 만들지 않는다.
- 사람이 글자를 넣을 수 있는 칸은 로그인 ID, 비밀번호, 받는 쪽 주소 셋뿐이다. 자유 입력란, 여러 줄 입력란, 파일 올리기, 가져오기, 내려받기를 만들지 않는다. 학생 번호는 고르는 칸이다.
- 앱이 받아들이는 변경은 평가 값 세 가지 중 하나를 고르는 것뿐이다. 글자를 받아 저장하는 요청이 없다.
- 받는 쪽은 번호·이름·반·종합의견·보호자·연락처가 그 번호의 가상 기록과 글자까지 같고, 평가 다섯 개가 각각 세 값 중 하나일 때만 저장한다. 가상 기록과 달라도 되는 값은 평가뿐이므로, 누군가 요청을 직접 만들어 보내도 사람이 쓴 글이나 실제 정보가 저장되지 않는다.
- 데이터는 메모리에만 둔다. 파일·데이터베이스·브라우저 저장소에 쓰지 않는다.
- 2부의 일지와 해석도 지어낸 것이고, 2부의 내용과 선택은 어디로도 보내지 않는다.
- 실제 정보를 넣기 위해 코드를 고치는 것도 금지다. README의 첫 경고에 그렇게 적혀 있다.
