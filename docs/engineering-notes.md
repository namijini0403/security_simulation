# 함정과 점검표

## 다른 기기 접속 스위치

### 끈 직후 다시 켜면 열리지 않았다
- **증상**: 스위치를 끄고 바로 다시 켜면 상태는 '켜짐'인데 내부 주소로는 연결이 되지 않았다.
- **원인**: 끌 때 닫은 문의 기록이 목록에 남아 있어서, 다시 켤 때 "이미 있는 문"으로 보고 새로 열지 않았다.
- **대응**: 문을 맞추는 작업(`syncOnce`)이 먼저 닫혔거나 듣고 있지 않은 기록을 치운 뒤 필요한 문을 새로 연다. 주소를 묶기 직전에 켜짐 상태를 한 번 더 확인하고, 여는 사이에 꺼졌으면 바로 닫는다. 문을 여닫는 작업은 줄을 세워 한 번에 하나만 한다. 이 부분을 고치면 `test/shared-switch.test.js`의 "끄기를 기다리지 않고 바로 다시 켜도", "켜는 도중에 끄면", "문을 여는 작업이 진행 중일 때 꺼도" 검사가 건너뜀 없이 통과하는지 본다.

### 같은 포트를 두 주소로 연다
- **사실**: Windows 11에서 `127.0.0.1:포트`와 `<내부 주소>:포트`를 서로 다른 서버로 동시에 여는 것이 된다(`exclusive: true`). 스위치는 이 방식으로 프로그램을 다시 실행하지 않고 범위를 바꾼다. macOS에서는 해 보지 못했다.
- **함정**: 같은 일을 `0.0.0.0`으로 한 번 열고 요청마다 보낸 주소로 거르는 방식으로 바꾸면 안 된다. 그러면 꺼져 있는 동안에도 다른 기기의 연결이 맺어지고 거절 응답이 나간다. "꺼짐"은 다른 기기에서 **연결 자체가 실패**하는 것이어야 한다.
- **확인**: 내부 주소가 있는 PC에서 `npm test` → `실제 내부 주소: 꺼져 있으면 연결 실패, 켜면 접속, 끄면 다시 실패`가 통과(건너뜀 아님).

### 타이머를 믿지 않는다
- **사실**: 30분 타이머가 늦게 울리거나(노트북 절전 등) 울리지 않아도, 제한 시간이 지난 뒤의 첫 요청·상태 읽기·켜기·연장 호출이 그 자리에서 스위치를 끈다(`expireIfDue`). 스위치의 새 진입점을 만들면 맨 앞에서 이것을 부른다.

### 같은 PC인데 '다른 기기 쪽 문'
- **증상**: 같은 PC의 브라우저로 `http://<이 PC 내부 주소>:4180/`을 열면 받는 쪽 화면이 403이다.
- **원인**: "같은 PC에서만"은 보낸 주소가 아니라 들어온 문으로 판단한다. 내부 주소로 들어오면 같은 PC라도 다른 기기 쪽 문이다. 접속 기록에는 '같은 PC'로 표시되지만(`samePc`) 허용 판단에는 `info.local`만 쓴다.
- **대응**: 의도된 동작이다. 화면은 `127.0.0.1` 주소로 연다. 둘을 섞어 "같은 PC면 허용"으로 바꾸지 않는다.

### 내부 주소로의 연결은 거절되는 데 약 2초가 걸린다 (Windows)
- **증상**: 듣는 프로그램이 없는 포트로 연결하면 `127.0.0.1`에서는 즉시(수~십수 밀리초) 거절되지만, 이 PC의 내부 주소로는 거절이 약 2초 뒤에 나온다(Windows 11에서 잰 값: 내부 주소 약 2.0초). 스위치가 꺼져 있을 때 내부 주소로 접속하는 경우, 받는 쪽 주소를 내부 주소로 넣었는데 받는 쪽이나 그 스위치가 꺼져 있는 경우가 여기에 해당한다. 다른 기기에서 걸리는 시간은 재 보지 못했다.
- **원인**: Windows는 같은 PC 주소가 아닌 곳으로의 연결이 거절되면 바로 실패로 알리지 않고 얼마간 다시 시도한다.
- **대응**: 진행 화면 서버는 받는 쪽 질의에 1.5초 제한을 걸고(거절을 끝까지 기다리지 않는다), 상태 요청은 진행 중인 질의를 0.3초만 기다린 뒤 직전 결과를 돌려준다. 그래서 받는 쪽에 닿지 못하는 동안에도 진행 화면의 1초 주기 갱신이 밀리지 않는다. 이 기다림을 늘리면 두 대로 진행하다 받는 쪽이 끊겼을 때 진행 화면 전체가 굼떠진다. 검사에서는 닫힌 내부 주소 여러 개를 차례로 두드리지 말고 한꺼번에 시도한다(차례로 하면 하나에 2초씩 든다). 발표에서는 ①의 "열리지 않는다"가 몇 초 뒤에 나올 수 있다.

## 두 앱

### 포트가 달라도 쿠키는 함께 간다
- **증상**: 1번 앱에 로그인한 브라우저가 2번 앱에서도 로그인된 것처럼 동작할 뻔했다.
- **원인**: 브라우저는 쿠키를 주소(호스트)로만 나누고 포트로는 나누지 않는다. `127.0.0.1:4173`과 `127.0.0.1:4174`는 같은 쿠키 통을 쓴다.
- **대응**: 두 앱의 쿠키 이름을 다르게 한다(`gsid_a`, `gsid_b`). 앱은 자기 이름의 쿠키만 읽고, 값은 자기 목록에 있을 때만 유효하다. 이름을 `a`/`b`가 아닌 뜻 있는 낱말로 바꾸면 금지 낱말 검사에 걸리거나 앱의 정체가 드러난다.
- **같은 이유로 생기는 일**: 한 대로 진행하면 옆 사람 화면과 같은 앱의 메인 화면이 같은 브라우저에서 로그인을 함께 쓴다. 옆 사람 화면에서 `parent01`로 로그인한 뒤 1번 앱 탭을 열면 로그인 화면 대신 학부모 화면이 먼저 보인다.

### 금지 낱말 검사에 평범한 낱말이 걸린다
- **증상**: 화면 문구에 '개인정보 보호', '안전하게'를 쓰거나 쿠키에 `Secure`, `SameSite=Strict`를 붙이면 검사가 실패한다.
- **원인**: 두 앱이 내보내는 모든 것에서 `secur`, `strict`, `guard`, `protect`, `safe`, `보호`, `안전`, `보안` 등을 찾는다. 낱말의 뜻이 아니라 글자를 찾으므로 무관한 쓰임도 걸린다.
- **대응**: 항목 이름 `guardianName`·`guardianPhone`과 '보호자'는 검사가 미리 떼고 본다. 그 밖에는 낱말을 바꾼다(상단 고정 표시가 '실제 개인정보 입력 금지'인 것도 이 때문이다). 쿠키는 `SameSite=Lax`를 유지한다. 새 항목 이름이 `guard`·`safe` 같은 글자를 품으면 예외를 늘리지 말고 이름을 바꾼다.

### 성적 저장은 전송이 끝나기 전에 대답한다
- **증상**: 성적 저장 직후 받는 쪽을 확인하는 검사가 가끔 0건을 본다.
- **원인**: 저장 응답은 받는 쪽으로의 전송을 기다리지 않는다(받는 쪽이 꺼져 있어도 저장이 느려지지 않게).
- **대응**: 검사는 받는 쪽이나 전송 기록을 보기 전에 `app.whenIdle()`을 기다린다. AI 초안은 전송을 기다린 뒤 대답하므로 해당 없다.

### 전체 초기화는 가는 중인 전송을 먼저 기다린다
- **증상**: 초기화 직후 받는 쪽에 한 줄이 남아 있었다.
- **원인**: 성적 저장의 전송이 아직 가는 중일 때 받는 쪽 지우기가 먼저 도착하고, 전송이 그 뒤에 도착했다.
- **대응**: 초기화는 두 앱의 `whenIdle()`을 최대 3.5초 기다린 다음 지우기를 보낸다. 앱 쪽에서는 초기화 전에 시작한 전송의 결과를 새 전송 기록에 넣지 않는다(세대 번호 비교). 공개 요청도 같은 방식으로, 도중에 초기화되면 결과를 버린다.

### 옆 사람 화면의 '요청한 사람'
- **증상**: 옆 사람 화면에서 `parent01`로 로그인한 뒤 같은 브라우저의 다른 탭에서 담임으로 바꿔 로그인하면, 옆 사람 화면은 계속 `parent01`이 요청했다고 적었다(진행 화면의 접속 기록에는 `teacher`).
- **원인**: 옆 사람 화면은 '요청한 사람'을 응답에서가 아니라 자기가 마지막으로 기억한 로그인으로 적는다.
- **대응**: 창이 다시 앞으로 올 때(`focus`, `visibilitychange`)마다 `GET /api/me`로 다시 물어 고친다. 창이 계속 앞에 있는 채로 서버 쪽에서 로그인이 풀리는 경우(전체 초기화 등)는 여전히 이전 값이 보인다.

### 반 전체 수집은 숨은 탭에서 느려진다
- **증상**: '반 전체 수집'을 누르고 다른 탭으로 넘어가면 인원 수가 아주 천천히 올라간다.
- **원인**: 수집은 요청 사이를 0.15초 타이머로 띄우는데, 브라우저는 가려진 탭의 타이머를 느리게 돌린다.
- **대응**: 수집이 끝날 때까지 옆 사람 화면을 맨 앞에 둔다(발표 안내서에 적혀 있다). 느려지는 정도는 재 보지 못했다.

### 진행 화면과 옆 사람 화면의 숫자가 잠깐 다르다
- **사실**: 수집 도중 옆 사람 화면이 10명일 때 진행 화면은 8~9명일 수 있다. 진행 화면은 1초마다 읽는다. 끝나면 같아진다. 고장이 아니다.

## 진행 화면

### 화면 안에 직접 쓴 모양·스크립트는 조용히 무시된다
- **증상**: 진행 화면이나 받는 쪽 화면의 HTML에 `style="…"`이나 `<script>…</script>`를 넣으면 아무 오류 없이 적용되지 않는다(브라우저 개발 도구에만 정책 위반이 찍힌다).
- **원인**: 두 화면은 `script-src 'self'; style-src 'self'`인 콘텐츠 보안 정책과 함께 나간다.
- **대응**: 모양은 CSS 파일의 클래스로, 동작은 JS 파일로 옮긴다. 스크립트에서 `element.style`도 쓰지 않는다. 성적 관리 앱의 화면에는 이 정책이 없어서 `style=` 속성이 동작한다 — 앱 화면의 코드를 진행 화면으로 옮길 때 걸린다.

### 문구를 고치면 문서 검사가 깨진다
- **증상**: `content.js`의 발표 문장 하나를 다듬었더니 `test/docs.test.js`가 실패한다.
- **원인**: 발표 안내서에 같은 문장이 글자 그대로 있어야 한다는 검사가 있다.
- **대응**: 문구를 고치면 `PRESENTER_GUIDE.md`(스위치 경고와 연결 확인 문구는 `NETWORK_GUIDE.md`도)의 같은 문장을 같은 커밋에서 고친다.

### 공개와 ④ 장면은 같은 학생에 걸려 있다
- **사실**: 공개의 다섯 시도는 `TEST-1001`과 `TEST-1002`를 쓴다. ④에서 이 둘 중 하나를 지우면 공개 표에 404가 그대로 나온다(실제 응답을 보여 주는 것이 규칙이므로 고쳐 주지 않는다). 그래서 진행 화면의 ④ 안내와 발표 안내서가 "가상학생01, 가상학생02가 아닌 학생"을 지우라고 한다. 공개가 쓰는 학생을 바꾸면 이 안내도 바꾼다.

### 받는 쪽에 쌓이는 줄 수는 장면마다 정해져 있지 않다
- **사실**: ③의 '내 아이 성적 고치기'만으로 온라인 표에 한 줄이 간다. 그래서 ④를 시작할 때 이미 1건이다. '공개'를 누를 때마다 한 줄씩 더 간다. 안내서나 검사에 "④에서 0건 → 1건" 같은 절대 숫자를 적지 않는다.

## 실행 파일

### `.bat`에 한글을 넣으면 실행 위치를 잃는다
- **증상**: 실행 파일의 실행되는 부분(`rem` 주석 줄 포함)에 한글이 있으면 그 뒤의 명령이 제대로 실행되지 않는다.
- **원인**: 한글을 깨지지 않게 보여 주려고 `chcp 65001`로 코드 페이지를 UTF-8로 바꾸는데, 그 뒤 cmd.exe는 실행하는 부분에 ASCII가 아닌 바이트가 있으면 파일에서 읽던 위치를 잃는다.
- **대응**: `exit /b %RC%`까지는 ASCII만 쓴다. 한국어 문구는 그 아래 `::[이름]문구` 줄에 두고(실행되지 않는 부분이다) `findstr`로 찾아 출력한다. `goto`와 `:이름표`를 쓰지 않는 것은 다른 이유다 — 줄 끝이 LF로 바뀐 채 내려받아져도 동작하게 하려는 것이다. 검사가 이 형식을 지키는지 본다.

### Node.js가 PATH에 없을 수 있다
- **증상**: 일반 셸에서 `npm test`나 `node`가 "찾을 수 없음"으로 실패한다.
- **원인**: fnm·nvm 같은 버전 관리 도구로 설치하면 그 도구가 준비해 준 셸에서만 `node`가 PATH에 있다.
- **대응**: 실행 파일은 PATH → fnm(기본, 22, 24 순) → nvm-windows의 연결 폴더 → 공식 설치 폴더 순으로 Node.js를 찾고, 찾은 것마다 22 이상인지 실제로 실행해 확인한다. 명령으로 돌릴 때는 Node.js 설치 폴더를 PATH 앞에 붙인다. Windows에서 `fnm exec --using=22 npm test`는 "program not found"로 실패한다(fnm이 `npm`을 실행 파일로 찾지 못한다). `fnm exec --using=22 node …`는 된다 — 실행 파일이 쓰는 방식이 이것이다.

### Ctrl+C 뒤에 창이 남는다
- **사실**: Windows에서 실행 파일로 띄운 창에서 Ctrl+C를 누르면 프로그램은 1~2초 안에 끝나지만 창에 계속할지 묻는 문장(Y/N)이 남는다. Y를 누르거나 창을 닫는다. 프로그램의 결함이 아니다.

## 검사

### `npm test`는 이 PC의 내부 주소에 잠깐 문을 연다
- **사실**: 스위치 검사가 실제로 내부 주소의 임의 포트에 수 초씩 문을 열었다 닫는다. 또 받는 쪽 주소 검사는 이 PC 것이 아닌 사설 주소(`10.255.254.253` 등)로 연결을 시도한다.
- **대응**: 학교·공용 와이파이에 연결된 채로 돌리지 않는다. 와이파이를 끄면 내부 주소 검사가 건너뜀이 되므로, 스위치를 고쳤을 때는 전용 연결(휴대폰 핫스팟 등)에서 돌린다.

### 검사 파일은 서로 다른 프로세스에서 동시에 돈다
- **증상**: 검사에서 고정 포트를 열면 다른 검사 파일과 부딪혀 간헐적으로 실패한다.
- **원인**: `node --test`는 파일마다 프로세스를 따로 띄워 나란히 돌린다.
- **대응**: 검사는 항상 포트 0을 쓴다. 받는 쪽 포트는 0으로 줄 수 없어서(앱이 보낼 고정 번호가 필요하다) 받는 쪽을 먼저 빈 포트에 띄우고 그 번호를 시연 프로그램에 넘긴다. "받는 쪽이 꺼져 있음"은 빈 포트를 열었다 닫아 얻은 번호로 만든다.

### 화면 폴더 없이 띄우는 검사
- **사실**: 앱 서버와 진행 화면 서버의 동작을 보는 검사 도구(`test/app-helpers.js`, `test/console-helpers.js`)는 앱과 받는 쪽의 화면 폴더를 없는 경로나 임시 폴더로 줘서 띄운다. 실제 화면 파일을 쓰는 것은 화면 파일 검사(`app-pages`, `console-pages`)와 처음부터 끝까지 검사(`e2e-*`)뿐이다. 화면 파일을 고친 뒤에는 이 검사들이 통과했는지를 본다.

## 점검표

### 앱에 요청을 하나 더할 때
1. `matchRoute`에 경로를 더한다.
2. `decide`의 2번 앱 쪽 `switch`에 그 요청의 규칙을 **반드시** 적는다. 적지 않으면 2번 앱에서는 기본값으로 403, 1번 앱에서는 누구에게나 열린다.
3. 응답으로 학생 기록이 나가면 접속 기록의 '나간 학생 기록'과 '가져간 것'에 넣을지 정한다(지금은 한 학생 조회와 반 전체 조회만 넣는다).
4. 받는 쪽으로 무언가 보낸다면 `forward`를 거친다. 목적지를 요청에서 읽지 않는다.
5. 두 앱의 응답이 번호와 거절 문구 말고는 같은지 본다.
6. 확인: `npm test`의 권한 표 검사와 두 앱 응답 비교 검사에 새 요청을 더하고 통과시킨다.

### 진행 단계를 더하거나 고칠 때
1. `src/console/content.js`의 `STEPS`만 고친다. `id`는 프로그램이 쓰는 이름이므로 기존 것을 바꾸지 않는다.
2. 공개 전에 나오는 문구에 금지 낱말이 없는지 본다.
3. 발표 안내서에 단계 이름과 말할 문장을 글자 그대로 넣는다.
4. 확인: `npm test`(문서 검사, 진행 화면 파일 검사).

### 스위치나 서버를 여는 코드를 고쳤을 때
1. 내부 주소가 있는 PC에서, 전용 연결에 붙여 `npm test`를 돌린다.
2. 출력의 `skipped`가 0인지 본다.
3. 시연 프로그램을 띄우고 스위치를 켠 뒤, 같은 PC에서 `http://<내부 주소>:4173/neighbor`는 열리고 `http://<내부 주소>:4170/`은 연결되지 않는지 본다. 끈 뒤에는 둘 다 연결되지 않아야 한다.
