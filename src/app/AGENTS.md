# src/app — 성적 관리 앱 (1번·2번 앱 공통)

## 맡는 것

- `server.js` — `createGradeApp(options)`가 앱 하나를 만든다. 요청 처리기, 학생 사본, 로그인 상태, 권한 판단, 받는 쪽으로 보내기, 접속 기록, 전송 기록, '가져간 것' 집계, 초기화.
- `public/` — 두 앱이 똑같이 내보내는 화면 파일. `index.html`+`index.js`(로그인, 학부모 화면, 담임 화면), `neighbor.html`+`neighbor.js`(옆 사람 화면), `styles.css`.

같은 코드를 두 번 불러 두 앱을 만든다. 달라지는 설정은 `label`('1번 앱'/'2번 앱'), `checkPermission`(거짓/참), `cookieName`(`gsid_a`/`gsid_b`) 셋뿐이다.

## 맡지 않는 것

- 포트를 열지 않는다. 처리기를 접속 스위치에 등록하는 것은 부르는 쪽의 일이다.
- 받는 쪽 주소를 정하지 않는다. 밖에서 받은 `getReceiverBase()`를 보낼 때마다 부를 뿐이다. 요청에서 목적지를 읽는 코드를 넣지 않는다.
- 보낸 주소가 사설 주소인지, 같은 PC인지 판단하지 않는다. 접속 스위치가 넘겨준 `info`를 기록에 옮겨 적을 뿐이다.
- 진행 화면에 무엇을 언제 보여 줄지(공개 전에 감추기 포함) 정하지 않는다. 접속 기록에는 '권한 확인 여부'를 항상 남기고, 감추는 것은 진행 화면 서버가 한다.
- `src/console/`, `src/receiver/`를 가져오지 않는다.

## 1번 앱의 결함은 의도된 것이다

`checkPermission`이 거짓인 앱은 요청자가 그 일을 해도 되는지 확인하지 않는다. 이것이 시연의 전부다.

- 고치지 않는다. `decide()`의 `if (!checkPermission)` 가지에 확인을 더하지 않는다.
- 넓히지 않는다. 허술함은 이것 하나다. 파일 실행, 임의 조회, 임의 주소 호출, 경로 벗어나기, 본문으로 목적지 지정 같은 다른 위험을 어느 앱에도 넣지 않는다.
- 이 코드를 다른 곳의 출발점으로 쓰지 않는다. 2번 앱 쪽도 접근통제 원리 하나를 보여 주는 비교용 예제일 뿐이다.

## 항상 성립해야 하는 것

**두 앱은 구분되지 않는다**
- `checkPermission`을 읽는 자리는 `decide()`와 접속 기록의 `permissionChecked` 두 군데뿐이다. 다른 곳에서 읽으면 두 앱이 권한 말고 다른 데서 갈라진다.
- 브라우저로 나가는 것(경로, 응답 본문, 머리글 구성, 쿠키 속성, 오류 문구, 화면 파일)에 어느 앱인지 드러나는 것이 없다. 같은 요청의 응답은 결과 번호와 거절 문구 말고는 두 앱이 같다.
- `public/`의 파일은 두 앱이 같은 바이트를 내보낸다. 앱 이름은 파일에 적지 않고 `GET /api/app`으로 받는다.
- 화면 파일과 응답에 `secur`, `safe`, `guard`, `protect`, `strict`, `보호`, `안전`, `보안`, `취약`, `허술`, `막아` 같은 글자를 쓰지 않는다(`guardianName`, `guardianPhone`, '보호자'만 예외).

**권한**
- 역할과 담당 학생은 `sessionOf(req)`가 돌려준 로그인 상태에서만 나온다. `decide()`에는 요청 이름, 경로의 학생 번호, 로그인 상태만 들어간다. 주소의 물음표 뒤, 본문, 머리글, 다른 쿠키를 권한 판단에 넘기지 않는다.
- 401/403은 404·400보다 먼저다. `decide()`를 학생이 있는지 찾기 전, 본문을 읽기 전에 부른다.
- 2번 앱에서 `decide()`가 모르는 요청 이름은 403이다(기본값). 새 요청을 더하면 `decide()`에 규칙을 적는다.
- 1번 앱에서 로그인을 요구하는 것은 한 학생 기록 조회(`getOne`)와 `me` 둘뿐이다.
- 접속 기록의 `permissionChecked`는 1번 앱에서 항상 거짓, 2번 앱에서 로그인·로그아웃만 거짓이다. 로그인했는지만 본 것은 확인으로 치지 않는다.

**데이터**
- 응답과 기록에 넣는 학생 기록은 항상 사본이다(`copyStudent`). 원본 객체를 밖으로 내보내지 않는다.
- 성적 저장은 본문에서 `ratings`만 읽는다. 과목·값이 하나라도 올바르지 않으면 아무것도 바꾸지 않는다.
- 바꿀 수 있는 것은 평가뿐이다. 글자를 받아 저장하는 요청을 더하지 않는다.

**보내기**
- 성적 저장이 성공하면 전체 기록을 `/sheet/rows`로, AI 초안 요청이 오면 `id`·`name`·`ratings`·`comment`를 `/ai/draft`로 보낸다. 삭제는 아무것도 보내지 않는다. 두 앱이 같다.
- 성적 저장의 응답은 전송을 기다리지 않고, 전송이 실패해도 200이다. AI 초안은 전송 결과를 기다리고 실패하면 502다.
- 목적지는 보낼 때마다 `getReceiverBase()`를 부르고 주소를 다시 확인해서 만든다. 확인을 통과하지 못하면 보내지 않고 전송 기록에 실패로 남긴다.
- `forward()`는 거절하지 않는 약속을 돌려준다. 실패는 결과 값에 담는다.

**기록**
- 처리기를 거친 요청은 빠짐없이 접속 기록에 한 줄 남는다(화면 파일, 404, 500 포함).
- '가져간 것'은 옆 사람 화면 표시가 붙은 요청 가운데 `getOne`·`list`가 200으로 내보낸 학생만 센다. 성적 저장의 응답, 공개 요청, 표시가 없는 요청은 세지 않는다. 명단은 따로 센다.
- 옆 사람 화면 표시는 기록에만 쓴다. `decide()`에 닿지 않는다.
- 기록의 줄은 만든 뒤 고정한다. 최근 2,000줄만 남기지만 '가져간 것'은 따로 모아 두어 줄이 밀려나도 줄지 않는다.

**초기화**
- `reset()`은 학생 20명, 로그인 상태, 접속 기록, 전송 기록, '가져간 것'을 처음으로 되돌린다. 초기화 전에 시작한 전송의 결과는 새 전송 기록에 넣지 않는다(세대 번호가 다르면 버린다).

## 화면 파일의 방식

- 서버가 준 값은 `textContent`로만 그린다. `innerHTML` 계열을 쓰지 않는다.
- 결과를 미리 적지 않는다. 옆 사람 화면은 결과 번호·학생 이름·'성공'·'실패' 같은 글자를 파일에 갖지 않고, 응답에서 받은 것만 그린다.
- 타이핑하는 칸은 로그인 폼의 두 칸뿐이다. 옆 사람 화면에는 입력 칸이 없고 학생 번호는 고르는 칸이다.
- 옆 사람 화면은 요청을 `ask()` 한 곳에서만 보내고 거기서 `X-Demo-Screen: neighbor`를 붙인다. 메인 화면은 이 표시를 붙이지 않고, 파일에 `neighbor`라는 글자도 없어야 한다.
- 옆 사람 화면의 단추는 일곱 개이고 순서가 정해져 있다. 이름이나 순서를 바꾸면 발표 안내서도 같이 바꿔야 문서 검사가 통과한다.
- 성적 저장 뒤의 문구는 "저장되었습니다"뿐이다. 다른 곳으로 보낸다는 말을 넣지 않는다.
- 메인 화면은 첫 주소(`/`)에서는 로그인하지 않은 상태로 명단을 불러오지 않는다. 두 앱의 첫 화면은 똑같이 로그인 화면이어야 한다.
- `/teacher`는 서버가 메인 화면 파일을 그대로 한 번 더 내주는 주소다(`TEACHER_PAGE_PATH`, 화면 파일 가지 안의 한 줄). 화면 스크립트는 `window.location.pathname`이 `/teacher`이면(`openedByAddress`) `GET /api/me`를 묻지 않고 담임 화면부터 그린다. 이 낱말이 하는 일은 그것과, 학생을 눌렀을 때 한 학생 조회 대신 `GET /api/students`를 받아 그 안에서 찾는 것(`askRecord`) 둘뿐이다. 요청을 만드는 `ask()`는 이 낱말을 모른다 — 머리글·본문·물음표 뒤에 무엇도 더하지 않는다. 서버 쪽에서도 이 낱말은 `decide()`에 닿지 않는다. 이 주소에 맞춰 서버가 자료를 더 내주게 하거나(새 요청, 새 가지), 화면이 거절을 가리거나 자료를 미리 적어 두게 고치지 않는다. 낱말을 바꾸면 `src/console/content.js`의 ③ 문구와 발표 안내서도 같이 바꾼다.
- 바깥 주소, `url()`, `@import`, 그림·영상 태그를 쓰지 않는다. 파일이 부르는 것은 같은 폴더의 파일뿐이다.
- 반 전체 수집의 간격은 `COLLECT_GAP_MS = 150`이라는 이름 붙은 값이다.
- 응답을 받지 못한 요청(서버가 꺼졌거나 연결이 끊김)은 두 화면 모두 `ask()`가 받아서 `{ status: null, failed: true }`로 바꾼다. 화면은 "연결하지 못했습니다"라고 적고 결과 번호를 지어내지 않는다(옆 사람 화면의 결과 번호 자리는 "응답 없음"). 반 전체 수집은 그 자리에서 멈추고 단추를 다시 누를 수 있게 한다. 받지 못한 요청은 거절로 세지 않는다.
- 알려진 한계: 옆 사람 화면의 '요청한 사람'은 응답이 아니라 화면이 기억한 로그인(`currentLogin`)에서 나온다. 창이 다시 앞으로 올 때 `GET /api/me`로 고친다(`refreshWho`). 또 조회·수집·고치기 요청을 서버가 들어주지 않으면(응답은 받았는데 결과 번호가 200이 아니면) 결과 줄을 적기 전에 `refreshWho`를 불러 그 대답대로 적는다(`confirmWho`). 다시 묻지 않는 경우: 응답을 받지 못했을 때, 200일 때, 기억하는 로그인이 없을 때, 마지막으로 물은 지 `RECHECK_GAP_MS`(2초)가 지나지 않았을 때. 다시 묻는 요청마다 접속 기록에 표시가 붙은 `GET /api/me` 한 줄이 남는다. 그래도 창이 계속 앞에 있는 채로 같은 브라우저의 로그인이 다른 사람으로 바뀌고 그 사람의 요청이 받아들여지는 동안에는, 창을 옮겼다 돌아오거나 요청이 한 번 거절될 때까지 이전 이름이 나온다.
- 늦게 온 `/api/me` 대답은 버린다. 로그인·로그아웃 단추와 `refreshWho`가 순번(`whoSeq`)을 올리고, 대답이 왔을 때 순번이 달라져 있으면 쓰지 않는다.
- 화면 스크립트는 200 말고 다른 결과 번호를 알지 못한다. 결과 번호(`status`)는 글자 그대로의 200하고만 견주고, 다른 번호를 글자로도 계산으로도(`400 + 1` 같은 식) 만들지 않는다. 어떤 거절인지 알아야 하면 번호로 가르지 말고 서버에 물어 그 대답을 쓴다. 숫자는 검사가 허용 목록으로 본다.

## 검사

- `test/app-permissions.test.js`(권한 표 전체, 404·400, 로그인 분리, 꾸민 역할), `app-forward.test.js`(보내기와 실패), `app-log.test.js`(접속 기록, 가져간 것, 두 앱 응답 비교), `app-pages.test.js`(화면 파일).
- 요청이나 권한을 고치면 권한 표의 모든 칸(두 앱 × 요청 × 로그인 없음·학부모 자기 아이·학부모 남의 아이·담임)을 다시 확인한다. 한 칸만 보는 검사를 더하지 않고 표 검사에 넣는다.
- 꼭 있어야 하는 경우: 1번 앱에서 로그인 없이 없는 번호 조회(404가 아니라 401), 2번 앱에서 학부모가 없는 번호에 성적 저장(404가 아니라 403), 역할·학생을 주소·본문·머리글·다른 쿠키로 꾸며 보내기(결과 불변), 한 앱의 쿠키를 다른 앱에 그대로 또는 이름만 바꿔 보내기(401), 성적 저장에 잘못된 과목 하나 섞기(전부 불변), 저장한 뒤 삭제(받는 쪽으로 아무것도 가지 않음), 받는 쪽이 꺼짐·오류·무응답·초안 없는 200일 때.
- 성적 저장 뒤 받는 쪽이나 전송 기록을 확인하려면 먼저 `await app.whenIdle()`.
- 검사에서 앱은 포트 0으로 띄우고, 받는 쪽은 임시 서버로 대신한다(`test/app-helpers.js`).
- 화면 파일을 고치면 `app-pages` 검사와 `e2e-edges`의 "두 앱의 화면 파일은 바이트까지 같고" 검사를 본다.
- `/teacher`는 `app-pages`의 "주소 끝의 낱말로 연 담임 화면" 묶음이 본다. 화면 스크립트를 흉내 화면 위에서 실행하되 요청은 진짜 두 앱 서버로 보낸다: 1번 앱에서 로그인 없이 명단과 누른 학생의 기록이 서버의 응답대로 그려지는 것, 2번 앱에서 서버의 거절 문장이 그려지는 것, 낱말·보낸 곳 머리글·물음표 뒤 값으로 2번 앱의 결과가 바뀌지 않는 것, `/`에서는 로그인 없이 명단을 부르지 않는 것.
